# 熔断探测预约优化设计

## 实际问题

丢失探测已有 cooldown 自恢复，不新增相同机制或持久化。
API 当前在构建可用目标列表时对所有后端调用 Allow。
如果首个后端成功，后续后端虽然没有请求，也已占用恢复探测机会。

## 方案

增加不修改状态的 `Available(backend)` 查询，返回与 Allow 相同的
可尝试性，但不创建条目、不预约探测。API 用它筛选候选，
完成能力检查并即将进入目标服务时才调用 Allow。
Allow 保持现有互斥和单探测约束；并发请求抢先获得探测时跳过该目标。
单目标与全开路时仍按现有策略强制尝试，不改变该兜底契约。

备选是保留提前预约并返回带标识的释放句柄。它需要处理过期预约、
旧请求释放新预约等并发问题，改动更大，本次采用延迟预约。

## 验证

先写失败测试：健康主目标成功后，冷却结束的备用后端仍保留探测机会。
补 Available 不消费探测的单元测试，以及并发 Allow 只放一个探测的测试。
保留并执行既有丢失探测恢复、400 不熔断、单目标强制尝试测试。
不缩短现有 cooldown，不把客户端取消或排队拒绝计为宕机。
